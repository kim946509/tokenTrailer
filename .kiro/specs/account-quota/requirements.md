# 계정 요금제 한도 상세 요구사항

상태: 검토용 초안 · 2026-10-19. [결정 목록](../README.md)을 따른다. F-18을 담당한다. 필수 3개 도구 모두 실제 한도 조회가 출시 조건이다. 아래 요구사항은 조회 가능성이 검증되었다는 선언이 아니다.

## AQ-01. 계정·요금제 연결

사용자 스토리: 사용자는 자기 계정의 요금제 한도를 기준으로 얼마나 사용했는지 알고 싶다.

- AQ-01.1 WHEN 한도 연결을 시작하면, 시스템은 대상 도구·계정·지원 요금제와 접근할 인증 정보, 외부 조회 목적 및 전송 범위를 설명해야 한다. 2026-10-20 승인된 D-10에 따라 기존 로그인 정보를 읽고 인증 갱신은 원래 도구에 맡겨야 한다. 만료 시 안내하며 TokenTrailer의 refresh grant와 원본 인증 파일 쓰기는 하지 않아야 한다.
- AQ-01.2 WHEN 연결에 성공하면, 시스템은 사용자가 구별할 수 있는 최소 계정 표시와 확인 가능한 요금제·한도 종류를 보여야 한다. 확인되지 않은 요금제를 임의로 추정하지 않아야 한다.
- AQ-01.3 WHILE 한도를 조회하면, 시스템은 토큰 사용 기록·프로젝트 경로·대화 원문을 한도 조회 목적으로 전송하지 않아야 한다. 인증 비밀정보를 화면·일반 설정·진단 로그에 노출하지 않아야 한다.
- AQ-01.4 IF 한도 연결이 해제되거나 인증이 만료되면, THEN 시스템은 로컬 토큰 분석을 계속 제공해야 한다. 계정 한도 상태는 연결 해제/인증 필요로 구분해야 한다.
- AQ-01.5 WHEN 연결을 해제하면, 시스템은 앱이 보관한 해당 연결의 비밀정보를 제거하고 한도 조회를 중단해야 한다. 원래 도구의 로그인 상태나 인증 파일을 수정하지 않아야 한다.

## AQ-02. 한도 100% 기준 사용률

사용자 스토리: 사용자는 계정에 맞는 전체 한도를 100%로 보고 남은 여유를 확인하고 싶다.

- AQ-02.1 WHEN 한도 응답을 받으면, 시스템은 제공자가 보고한 사용률 또는 같은 계정·같은 창·같은 단위의 사용량/한도에 근거해 사용률을 표시해야 한다.
- AQ-02.2 IF 사용량과 한도가 주어지면, THEN 시스템은 사용량 ÷ 한도 × 100으로 사용률을 계산해야 한다. 남은 비율만 주어지면 의미가 확인된 경우에만 100에서 차감해야 한다.
- AQ-02.3 IF 서로 다른 시간 창·모델 그룹·한도 종류가 있으면, THEN 시스템은 이름·적용 범위·사용률·초기화 시각을 각각 표시해야 한다. 이 비율들을 더하거나 평균 내어 하나의 계정 사용률로 만들지 않아야 한다.
- AQ-02.4 IF 한도가 없거나 0·무제한·미확인·미지원이면, THEN 시스템은 유효한 사용률을 만들어내지 않고 해당 상태를 표시해야 한다. 제공자가 확인한 실제 사용률 0%는 오류와 구별해야 한다.
- AQ-02.5 WHEN 사용률을 표시하면, 시스템은 수집된 로컬 토큰 비율과 분리해야 한다. 구독 가격, 추정 토큰 최대치, 다른 PC에서 관찰되지 않은 기록으로 분모를 만들어내지 않아야 한다.
- AQ-02.6 IF 제공자 값이 100%를 넘거나 계약과 맞지 않으면, THEN 시스템은 실제 초과와 잘못된 응답을 계약에 따라 구분하고 조용히 100%로 잘라 정상값처럼 보여주지 않아야 한다.

## AQ-03. 초기화 시각·최신성

사용자 스토리: 사용자는 언제 한도가 초기화되는지와 정보가 최신인지 알고 싶다.

- AQ-03.1 WHEN 초기화 시각이 제공되면, 시스템은 표시 시간대와 절대 시각 및 남은 시간을 해당 한도 창에 연결해 표시해야 한다.
- AQ-03.2 IF 초기화 시각이 제공되지 않거나 rolling window라 고정 시각이 없으면, THEN 시스템은 미확인 또는 이동 창이라는 실제 의미를 표시하고 임의의 초기화 시각을 생성하지 않아야 한다.
- AQ-03.3 WHEN 표시된 초기화 시각이 지나면, 시스템은 재조회 전 사용률을 자동 0%로 확정하지 않아야 한다. 확인 대기 또는 오래된 상태를 표시해야 한다.
- AQ-03.4 WHEN 한도를 갱신하면, 시스템은 로컬 수집과 별도 상태·마지막 성공 시각을 제공해야 한다. 사용자가 자동 갱신 주기를 선택할 수 있게 하고 수동 갱신을 제공해야 한다(2026-10-20 사용자 요청). 선택지는 5/15/30/60/300초, 연결별 설정과 기본 300초를 AICap 선례로 제안하되 제공자 rate limit/Retry-After를 우선해야 한다.
- AQ-03.5 IF 네트워크 오류·인증 만료·rate limit이 발생하면, THEN 시스템은 해당 상태와 재시도 가능 시점을 알리고 이전 성공값을 오래된 값으로 표시해야 한다. 중복 동시 요청과 무한 즉시 재시도를 방지해야 한다.
- AQ-03.6 IF 계정이 바뀌면, THEN 시스템은 이전 계정의 한도를 새 계정 값으로 보여주지 않아야 한다. 계정별 캐시 범위를 구별하고 새 계정 조회 상태를 표시해야 한다.

## AQ-04. 출시 기준과 지원 경계

사용자 스토리: 사용자는 지원한다고 명시된 도구에서 실제 자신의 요금제 한도를 확인하고 싶다.

- AQ-04.1 WHEN 출시를 판정하면, 검증 담당자는 Claude Code·Codex·Gemini CLI 각각 승인된 계정·요금제에서 실제 한도 응답과 앱 표시가 일치함을 확인해야 한다. 모의 응답·미지원 안내만으로 필수 기능 완료를 인정하지 않아야 한다.
- AQ-04.2 WHEN 지원 범위를 명시하면, 시스템은 도구 이름뿐 아니라 지원 로그인 방식·요금제·한도 창·초기화 정보 유무를 명시해야 한다. 하나의 요금제 검증을 모든 계정 지원으로 확대하지 않아야 한다.
- AQ-04.3 IF 필수 도구의 필요한 조회 경로를 확보할 수 없으면, THEN 개발 과정에서 근거와 대안을 사용자에게 보고하고 요구사항 변경 검토를 받아야 한다. 추정값으로 대체하거나 출시 조건을 임의로 완화하지 않아야 한다.

## 수용 시나리오와 미결 조사

| 사례 | 기대 결과 |
|---|---|
| 사용 25/한도 100; 남은 비율 60% | 각각 사용률 25%, 40% |
| 단기 창 25%, 주간 창 80% | 두 이름과 초기화 정보 표시. 합계 105%나 평균 52.5% 생성 금지 |
| 정상 0% 이후 연결 오류 | 이전 0%와 오류·마지막 성공 시각 동시 표시 |
| 초기화 시각 통과 후 재조회 실패 | 확인 대기/오래됨, 자동 0% 전환 금지 |
| 계정 A에서 B로 전환 | A 값이 B 요금제 한도로 노출되지 않음 |

검증 과제: 도구별 로그인 방식·계정 종류·요금제에 따른 실제 조회 경로와 응답 의미, 원본 클라이언트 영향, 요청 제한, 초기화 시각 제공 여부를 지원 행렬로 검증한다. 사용자 개인 요금제는 시험 환경 중 하나이며 제품 지원 범위를 정하는 기준이 아니다. Gemini는 CLI만 범위에 유지하고 Antigravity 지원 여부는 추후 검토한다. 실계정이 없는 조합은 모의 응답 검증과 구분해 미검증으로 남기며, 개인에게 해당 서비스 가입을 요구하지 않는다. AICap과 같은 표시 목표가 동일 조회 방식 채택을 뜻하지 않는다.

검증 연결: V-03, V-05, V-06. 로컬 토큰 기록의 지원과 계정 한도 조회 지원은 별개로 판정한다. 금액·구독료 대비 금전적 효율 계산은 범위 밖이다.
