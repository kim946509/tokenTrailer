# AICap 전체 기능 분석

조사일: 2026-10-19. 설치된 AICap 0.7.5의 배포 파일을 기준으로 조사했다.

## 결론과 범위

AICap은 **여러 AI 계정의 요금제 한도 모니터링과 계정 관리**를 중심으로, 트레이·위젯·작업표시줄 표시, 인증정보 관리, 외부 개발 도구 계정 전환, 사용 창 스케줄러, 백업·복원까지 제공한다.

전체 화면의 기능과 프런트엔드 호출 경로를 조사하고, 네이티브 하위 시스템 및 작업표시줄·자동 시작의 주요 함수를 분석했다. 이는 모든 네이티브 함수를 해석하거나 모든 기능을 실행 검증했다는 뜻은 아니다. 로그인, 계정 전환, 사용량 초기화, 자동 채팅, 백업 복원, 업데이트 설치는 실행하지 않았다. 앱·설정·인증정보와 프로젝트 요구사항은 변경하지 않았다.

주요 구분:

- 화면 중심 지표는 토큰 수가 아닌 **사용 한도 이용률과 초기화 시각**이다.
- 네이티브에는 Codex 토큰 통계 필드도 있다. 따라서 토큰 통계 기능이 전혀 없다고 단정할 수 없다. 해당 필드의 화면 연결은 미확정이다.
- 시간대·작업·세션·현재 PC별 토큰 분석 화면은 조사한 프런트엔드에서 찾지 못했다.
- 아래의 오류 후보는 코드 경로에서 도출한 것이다. 사용자가 겪은 재부팅 후 미표시 현상의 확정 원인은 아니다.

## 데이터 수집과 표시 구조

메인 화면은 인증 상태가 준비된 계정에 대해 `refresh_provider_usage`를 호출한다. 제공자별 네이티브 계층이 외부 응답을 정규화하고 화면은 `five_hour`, `seven_day`, `extra_windows`의 `utilization`, `resets_at`, `plan_type` 등을 표시한다. 프런트엔드 갱신 간격과 실제 외부 API 요청 수가 항상 같다는 보장은 없다.

위젯은 `get_provider_usage_data_all`로 백엔드의 사용량 데이터를 약 1초마다 조회한다. 이를 매초 외부 제공자 API를 호출하는 것으로 해석하면 안 된다. 배지 조회도 별도 경로다.

| 제공자 | 네이티브 정적 근거 | 해석 |
|---|---|---|
| Anthropic | OAuth usage/profile/messages, usage_reset 모듈 | 사용률 조회 외 채팅 및 초기화 경로 포함 |
| OpenAI | wham/usage, profiles/me, reset-credits, consume, codex/responses | 사용량·통계·초기화·모델 요청의 구분 필요 |
| Google | cloudcode 계열 usage/chat | Antigravity 관련 기능으로 보이며 범용 Gemini API 집계로 단정 불가 |
| Z.ai | quota/limit, chat/completions | API 키 기반 한도 조회·모델 요청 경로 |

Codex 네이티브에는 `lifetime_tokens`, `peak_daily_tokens`, `daily_usage_buckets`, `cumulative_daily_usage_buckets`, `weekly_usage_buckets`, `total_threads`, `workspace_rank`, `stats_as_of`가 있다(`PE+0x941e5a` 이후). 메인 JS에는 해당 통계 식별자가 발견되지 않았다. 타입만 남았는지, 호출하지만 표시하지 않는지, 다른 경로에서 쓰는지는 미확정이다. 이 필드가 현재 PC에서 사용한 토큰이라는 근거도 없다.

추가 Ghidra 조사에서 `wham/profiles/me`와 `openai/api/statistics.rs` 문자열(`0x1408685e2`)을 참조하는 명령 위치 `0x1403c3749`를 확인했고, 이는 `0x1403c3540` 함수에 속한다. 따라서 통계 관련 문자열에 실제 코드 참조는 있다. 그러나 해당 함수의 의사 코드 복원 중 존재하지 않는 메모리로의 흐름 경고가 발생하여 조사용 디컴파일 프로세스를 중단했다. API 호출 완료·응답 사용·UI 도달성까지 확인한 것은 아니다.

추가 근거 ID:

- 문자열: `ev_7d60ebe47920e74ef35512f7379f4f8fde68f4f4a5cdd2f51eee76938af1a415`
- 코드 참조: `ev_8429b8da4b4f1f30b7274a0b19340fbf3e5989f7a2ec1470f07b690407163850`
- 함수 경계: `ev_7b92fd76a37319ecfb3945508c204c2c31ab388ad33801b321d573a4b0825173`

스케줄러 파일 문자열에도 코드 참조는 있었으나 조회한 두 위치는 Ghidra가 함수로 정의하지 못한 영역이었다. 정확한 발동 조건을 복원하지 못했으며, 기능 설명·모듈·코드 참조 수준으로 남긴다.

## 작업표시줄과 자동 시작

자동 시작은 **프로세스가 실행되는가**, 트레이로 시작은 **실행 시 메인 창을 어떻게 표시하는가**, 작업표시줄 위젯은 **별도 위젯을 Explorer 작업표시줄에 붙일 수 있는가**의 문제다. 같은 현상처럼 보여도 실패 지점은 다르다.

| 단계 | 확인한 구현 | 근거 |
|---|---|---|
| 자동 시작 등록 | HKCU Run 값 및 StartupApproved 데이터 기록 | `0x1407148e0` |
| 기존 등록 마이그레이션 | 조건에 따라 기존 등록 삭제 후 활성화 | `0x140341fe0`; 진입 조건 전체는 미확정 |
| 작업표시줄 탐색 | Shell_TrayWnd / Shell_SecondaryTrayWnd, 모니터 대응 | `0x1407d5050` |
| 위젯 부착 | 원래 부모·스타일 보관 후 SetParent, 실패 반환 | `0x1407d53b0` |
| 연결 유효성 검사 | HWND·클래스·위치·모니터 확인, 필요 시 재탐색/부착 | `0x1407d3730` |
| 갱신 | 재검사·재배치, 특정 오류에서 핸들 초기화 후 한 번 재시도 | `0x1407d3590` |
| 공간 계산 | DPI, ReBarWindow32/TrayNotifyWnd, UI Automation 경계, 여유 공간 | `0x1407d3a50` |
| 이벤트 감시 | WinEventHook, 이벤트 필터와 debounce | `0x1407d6660`, `0x1407d67b0` |

공간 계산 결과에 따라 위젯을 숨길 수 있으므로 프로세스가 실행 중이어도 작업표시줄에 나타나지 않을 수 있다. Explorer가 재시작되어 PID/HWND가 바뀌었을 때 감시 hook을 완전히 재등록하는지는 확인하지 못했다. 부착 함수 내부에는 지연 재시도 루프가 보이지 않지만 상위 경로 전체에 재시도가 없다는 뜻은 아니다.

분석 중 2026-10-19 약 13:22에 확인한 설정은 autoStart=true, 트레이로 시작=true, widgetVisible=true, **widgetMode=floating**이었다. 자동 시작 레지스트리와 실행 중 프로세스도 확인했다. 이는 해당 시점의 상태이며 사용자가 오류를 겪던 부팅 시점의 상태를 입증하지 않는다.

| 위젯 조회 오류의 가시성 부족 | `wo`, JS 260264–264392: 오류 로깅, 명시적 오류 UI 모델 없음 | 오래된 값/미갱신 상태를 알아보기 어려울 가능성 |
| 인증 가능 계정이 없으면 위젯 설정 비활성화 | 인증 조회 완료 후 표시 가능 여부를 보고 widgetVisible=false 저장 | 일시적 인증 오류와 실제 계정 부재가 어떻게 구분되는지 런타임 검증 필요 |
| NOT_FOUND와 주기 갱신 | `In`, JS 16051–17061: retry=false이나 주기 자체는 별도 | 즉시 재시도 중단과 주기 조회 중단을 혼동할 수 있음 |
| 작업표시줄 공간 부족 | 레이아웃 함수의 가시성 반환 | 등록·실행 성공 상태에서도 위젯 숨김 가능 |
| 자동 시작 등록 마이그레이션 실패 | 삭제 후 재등록 경로 | 삭제 성공/재등록 실패 조합의 영향 확인 필요; 실제 발생 증거 없음 |
| 불투명도 키보드 조작 저장 | slider 저장이 onMouseUp에 연결 | 키보드 조작의 영속화 여부 미검증 |

이 후보 중 하나를 사용자의 실제 오류 원인으로 확정하려면 로그인 시점 프로세스 시작, 설정 읽기, Explorer 준비, 위젯 생성·부착·가시성 전환을 같은 시간축으로 관찰해야 한다.

## 계정·백업·외부 전송에서 확인한 주의점

- 인증정보 화면에는 복사 가능한 원문 필드가 있다. 실제 인증정보는 조사하지 않았다.
- keyring 모듈, CredReadW/CredWriteW, 분할 Base64 저장 단서가 있다. Base64 자체는 암호화가 아니며 OS 저장 보호의 세부 속성은 미검증이다.
- 백업 UI는 설정과 인증정보를 포함한다고 안내한다. 로컬 복원은 현재 정보를 대체하고 재시작하는 흐름이다. 네이티브에는 비밀번호·크기·버전·profile/credential 정합성 검사 및 rollback 실패 경로가 있다. 복원 원자성을 보장한다고 단정하지 않는다.
- Drive 복원 후 백업 삭제 선택은 기본 true다. 삭제 실패 안내와 앱 재시작은 별도로 처리한다.
- 사용 창 스케줄러는 단순 알림이 아니라 모델 요청을 발생시킬 수 있다. 정확한 요청 내용·대상 모델·중복 방지는 추가 확인 대상이다.
- 피드백 네이티브 경로에 `logFile`과 로그 읽기·multipart 구성 단서가 있다. 텍스트만 전송한다고 설명해서는 안 된다. 실제 첨부 범위와 민감정보 제거는 미검증이다.
- analytics 이벤트 및 protobuf relay 경로가 있다. 이것만으로 전송된 데이터나 동의 처리의 적정성을 판단하지 않는다.

## TokenTrailer 목표와의 대응

아래는 기존 목표에 대한 조사 결과의 대응이며 새 요구사항을 확정한 것이 아니다.

| 사용자 목표 | AICap에서 참고할 부분 | 별도 설계가 필요한 부분 |
|---|---|---|
| Claude·Codex 필수 | 다중 계정, 인증 상태, 사용 창·갱신 정책 | CLI/앱별 실제 토큰 출처, 계정·세션 매핑, 누락 처리 |
| 안정적인 작업표시줄·위젯 | 표시 모드, 모니터·DPI·레이아웃·재바인딩 | 로그인/Explorer 재시작/모니터 변경 검증, 실패 상태 표시와 복구 기준 |
| 언제 많이 사용했는가 | 초기화 시각·마지막 갱신 표시 | 소비 이력 저장, 시간대 집계, 실제 토큰·비용·한도 사용률 구분 |
| 어떤 작업에서 많이 사용했는가 | 조사한 UI에서 해당 기능 미발견 | 프로젝트·세션·작업 정의, 태깅, 중복 집계 방지 |
| 이 PC 사용량 및 전체 대비 비율 | 계정 단위 조회와 로컬 도구 연동 구조 | 동일 계정·기간·지표의 전체 분모 확보; 현재 PC와 개인 사용자 구분 |
| Grok·Gemini·Kimi 확대 | Google/Antigravity 연동은 참고 가능 | Grok/Kimi 실제 연동 미발견; Gemini 제품별 데이터 경계 별도 조사 |

계정 한도 사용률과 로컬 토큰 수를 나누어 PC 비중을 계산하면 단위가 맞지 않는다. 전체 집계가 없으면 PC 사용량만 보여주고 전체 대비 비율은 미확인으로 남겨야 한다.

## 분석 완료 기준과 남은 부분

완료한 범위는 노출 기능 목록, 프런트엔드 호출·상태 흐름, 네이티브 하위 시스템 지도, 작업표시줄·자동 시작의 선택적 함수 분석, TokenTrailer 목표와의 차이 정리다.

미완료 범위는 모든 네이티브 함수의 복구, 외부 API 응답 검증, 실제 계정 전환·초기화·백업 복원·업데이트, 부팅 및 Explorer 재시작 재현, Codex 통계의 실제 도달성, 스케줄러의 정확한 발동 조건과 중복 방지, 전송 payload 및 저장 보호 세부 검증이다.

Ghidra 기본 분석은 Decompiler Switch Analysis 단계에서 장시간 지연되어 해당 분석기만 비활성화한 설정을 사용했다. 함수 의사 코드와 일부 교차 참조는 확보했지만 간접 호출 관계가 빠질 수 있다. 검색 결과가 없다는 사실만으로 기능이나 호출이 없다고 결론 내리지 않는다.

이번 확장 분석의 초기 분석·검색은 14:02:10–14:10:07(KST), 약 8분이었다. 이전 결과를 포함한 Evidence 56개를 `comprehensive-native-evidence.json`, 스냅샷을 `comprehensive-native-snapshot.json`에 내보냈고 로그도 보관했다. 14:14에 REA 네이티브 세션을 닫고 조사용 Java/디컴파일 프로세스 종료를 확인했다. 도구의 `unknowns: 0`은 내보내기 메타데이터이며, 이 문서에 명시한 기능상 미확정 사항이 없다는 의미가 아니다.
