# AICap 네이티브 집중 분석 결과

2026-10-19. 앞선 60분 시간 초과 이후, 사용자 승인에 따라 `Decompiler Switch Analysis`만 제외한 별도 프로필로 조사했다. 앱 구현이나 설정 수정은 하지 않았다.

## 결과와 분석 조건

- 동일 대상: AICap 0.7.5의 `ai-cap.exe`. SHA-256 `232aa2d803e9cc551027d0996637122e6c4f3845d1a86546c3cfd4be32f02b3a`를 REA가 재확인했다.
- Ghidra 12.1.4 / REA 6.5.0. 환경 변수는 조사용 서버에만 적용했다. 영구 설정 변경 없음.
- 프로필: `ghidra-default+disabled:Decompiler Switch Analysis`, digest `d55962fed3aed661acdc1bf131dd0edbad53d517dc897ade86195d22bfc19ee2`.
- 13:10:59 검색 요청 시작 → 13:18:58 결과 반환(KST). 약 8분 만에 초기 분석과 검색을 완료했다. 초기 대기 한도는 20분이었다.
- 작업표시줄 문자열 28개, 선택한 함수 15개의 의사코드, 그중 4개 함수의 상세 분석을 확보했다. 전체 앱 분석 완료를 뜻하지 않는다.
- `focused-native-evidence.json`: Evidence 48개 보관. 함수별 ID는 `focused-function-index.json`에 기록했다.

## 작업표시줄 구현: 코드로 확인한 사실

### 1. 작업표시줄 창에 위젯 창을 붙인다

`0x1407d5050`은 `EnumWindows`와 콜백 `0x1407d5260`을 통해 `Shell_TrayWnd`, `Shell_SecondaryTrayWnd` 클래스의 창을 찾는다. 모니터 조건에 맞는 대상을 선택하는 경로와 기본 작업표시줄로 돌아가는 경로가 있다.

`0x1407d53b0`은 기존 부모 창과 창 스타일을 저장하고, `SetParent(widget, taskbar)`를 호출한다. `SetLastError(0)` 후 반환값과 `GetLastError()`를 함께 검사한다. 작업표시줄 창을 못 찾거나 연결이 실패하면 오류 결과를 반환한다. 이 함수 내부에서 부팅 준비를 장시간 기다리는 반복은 확인되지 않았지만, 상위 호출부 전체의 재시도 부재를 뜻하지 않는다.

이제 `SetParent` 사용은 문자열만의 추론이 아니라 실제 호출 코드로 확인됐다. 일반 앱 아이콘이나 시계 옆 트레이 아이콘과는 다른, 작업표시줄에 사용량 위젯을 삽입하는 경로다.

### 2. 재연결 경로가 존재한다

`0x1407d3730`은 저장된 작업표시줄 핸들에 `IsWindow`, 클래스 이름, `GetWindowRect`, 모니터 조건을 검사한다. 유효하지 않으면 작업표시줄을 다시 찾고 `SetParent`로 연결한다.

`0x1407d3590`은 연결 상태를 확인한 뒤 위 검증·재연결과 레이아웃 계산을 수행한다. 특정 `taskbar` 레이아웃 오류에서는 저장 핸들을 비우고 다시 찾은 후 레이아웃 계산을 한 차례 더 수행하는 분기가 있다.

따라서 “Explorer가 바뀌어도 재연결 처리가 전혀 없다”는 설명은 맞지 않는다. 다만 Explorer 재시작 뒤 이 경로가 실제로 다시 호출되는지는 별도 문제다.

### 3. 표시할 공간을 계산하며, 조건에 따라 표시 상태가 false가 된다

`0x1407d3a50`은 다음 요소를 이용해 위젯 위치와 표시 가능 여부를 계산한다.

- 작업표시줄과 `ReBarWindow32`, `TrayNotifyWnd`의 영역.
- `GetDpiForWindow`와 DPI 컨텍스트, 좌표 변환 `MapWindowPoints`.
- COM 기반 UI 요소 탐색, 요소의 프로세스·종류·영역 확인.
- 위젯 폭을 DPI 비율로 변환하고 사용 가능한 좌우 경계와 비교.

복원된 의사코드에서는 픽셀 폭이 15보다 크고, 계산된 위젯 왼쪽 위치가 기준 영역 안에 있으며, 앞선 요소의 오른쪽 경계와 최소 간격을 만족할 때 표시 가능 플래그가 true가 된다. 숫자 조건은 복원 코드 기준이며 UI 옵션과 일대일로 대응한다고 단정하지 않는다.

가능할 때 `ShowWindow`, `SetWindowPos`, `SetWindowRgn`으로 표시·배치·클리핑한다. `0x1403af880`은 레이아웃 결과를 표시 상태 처리 함수 `0x1403af9b0`으로 전달한다. 이 처리에는 `taskbar-widget-visibility` 이벤트와 `aicap-taskbar-widget-fade-hide` 이름의 숨김 작업이 연결된다.

따라서 프로세스가 실행 중이어도 표시 공간 계산 때문에 위젯이 보이지 않을 수 있는 코드 경로가 있다. 이것이 사용자가 겪은 실제 오류 원인이라는 재현 증거는 아직 없다.

### 4. 이벤트로 레이아웃 변경을 감시한다

`0x1407d6660`은 특정 프로세스 ID를 인자로 `SetWinEventHook(0x8000, 0x800b, ..., callback, pid, 0, 2)`를 등록하고 메시지 루프를 실행한다. 콜백 `0x1407d67b0`에는 일부 이벤트 필터와 후속 처리를 묶는 경로가 있다.

Explorer가 재시작해 프로세스 ID가 바뀌었을 때 감시 훅이 재등록되는지, 최초 연결 실패 후 다시 시도하게 하는 상위 경로가 무엇인지는 이번 범위에서 확정하지 못했다. 이 부분이 후속 검증 지점이지, 이미 확인한 결함은 아니다.

## 자동 시작 구현과 현재 상태

`0x1407148e0`은 HKCU 아래 Run 경로를 열고 `RegSetValueExW`로 실행 명령을 저장한다. 이어 StartupApproved 경로에 12바이트 값을 저장하는 코드도 있다. `0x1407153b0`은 Run의 값을 `RegDeleteValueW`로 삭제한다.

레지스트리 경로의 의사코드 표시가 잘못된 UTF-16 문자열처럼 보였으므로, `0x1408ff600`의 원시 바이트를 별도로 읽어 ASCII 경로를 확인했다. `0x1408ff61b`는 `SOFTWARE\Microsoft\Windows\CurrentVersion\Explorer\StartupApproved\Run`, `0x1408ff661`은 `SOFTWARE\Microsoft\Windows\CurrentVersion\Run`의 시작 위치다.

`0x140341fe0`에는 `migrate_auto_start::Here` 기록과 함께 조건부로 삭제 함수 → 등록 함수를 호출하는 경로가 있다. 재등록 실패를 처리하는 분기도 확인했다. 따라서 해당 마이그레이션이 실행되고 삭제는 성공했지만 재등록이 실패한다면 등록이 비는 가능성은 있다. 그러나 해당 분기의 정확한 진입 조건, 과거 실제 실행 여부와 실패 여부는 확정하지 못했고, 이것이 설정값 false를 만든다는 근거도 없다.

이번 조사에서 다시 읽은 현재 상태:

| 항목 | 현재 관찰 |
|---|---|
| `isAutoStartOnBoot` | `true` |
| `isStartInTray` | `true` |
| `isWidgetVisible` | `true` |
| `widgetDisplayMode` | `floating` |
| HKCU Run의 AICap 값 | 설치된 `ai-cap.exe` 실행 경로가 존재 |
| StartupApproved의 AICap 값 | `02-00-00-00-00-00-00-00-00-00-00-00` |
| settings.json 수정 시각 | 2026-10-19 10:53:18 |

이전 조사 시점의 `false`/등록 없음과 현재 상태는 다르다. 이번 조사에서 설정이나 등록을 변경하지 않았다. 이전 관찰을 현재에도 꺼져 있다는 결론으로 사용하면 안 된다. 현재는 floating 모드이므로 이번에 분석한 taskbar 삽입 경로가 현재 표시 실패에 사용되고 있다고도 단정할 수 없다.

## 한계와 검증 상태

- 정적 분석으로 구현 경로를 확인한 결과다. 사용자 증상의 단일 원인을 확정하거나 오류를 재현한 결과가 아니다.
- 분기 분석기 제외, 심볼 부재, 미해결 간접 호출 및 함수 경계 누락이 있다. 일부 함수에 타입 추론·점프 테이블 경고가 남아 있다. 문자열이나 빈 호출자 목록만으로 코드 부재를 단정하지 않았다.
- 연결·레이아웃 함수의 호출 관계는 REA에서 `partial`로 보고됐다. 원래 Rust 변수명·타입·오류 enum 의미는 모두 복원된 것이 아니다.
- 실제 로그인/재부팅, Explorer 재시작, 모니터·DPI 변경, 작업표시줄 공간 부족 재현은 수행하지 않았다.
- 확보한 의사코드는 원본 소스가 아니며 컴파일용 코드로 사용하지 않는다.
- 앱 실행 파일, 앱 설정, 자동 시작 등록, 프로젝트 구현 파일은 변경하지 않았다.
