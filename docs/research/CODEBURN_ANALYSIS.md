# CodeBurn 분석

조사일: 2026-10-19. AICap 후속 비교 분석이며 앱 구현·설정 수정은 하지 않았다.

## 핵심 결론

CodeBurn은 **로컬 AI 도구의 세션 기록을 수집하여 토큰·비용·활동·프로젝트·세션별로 분석하는 제품**이다. 계정 한도 조회에 초점을 둔 AICap보다 TokenTrailer의 소비 이력 분석 목표에 더 직접적인 참고 대상이다.

다만 다음 세 가지를 구분해야 한다.

1. 로컬 기록에서 관찰한 토큰과 문자 수로 추정한 토큰.
2. 토큰에 가격표를 적용한 비용과 구독료·실제 청구액.
3. 현재 PC의 관찰 데이터, 연결된 기기의 합계, 제공자 계정의 한도 사용률.

CodeBurn의 웹 화면에는 **토큰/비용 전환과 시간 단위 그래프**가 있다. '그래프가 없어서 어렵다'기보다는 여러 분석 축과 서로 다른 지표가 한 제품에 함께 있어 해석 부담이 생긴다는 것이 이번 조사자의 판단이다. 실제 사용자 테스트로 입증한 결론은 아니다.

## 사용량과 추정치

공통 모델은 input, output, cache creation, cache read, cached input, reasoning 등을 별도 필드로 보유한다(`src/types.ts:3`). 제공자별로 cache가 input에 포함되는 방식이 다르므로 모든 원시 필드를 무조건 더해서는 안 된다. 실제 정규화·비용 계산은 제공자별 구현을 따라야 한다.

특히 **시간 그래프의 Tokens는 fresh input + raw output**이다(`src/granular-history.ts:355-358`). 캐시와 별도 reasoning은 제외하지만, 일별 다른 집계는 제공자별 billable output과 cache read/write를 별도로 다룬다. 따라서 같은 기간의 '토큰'이라는 라벨만으로 수치가 같아야 한다고 가정할 수 없다. TokenTrailer에서는 이 정의를 화면 간 일관되게 유지할 필요가 있다.

비용은 모델 단가·캐시·속도·검색 요청 등에 따른 계산값이며 청구서 검증값이 아니다. 미등록 모델의 가격을 찾지 못하면 경고 후 0을 반환하는 경로가 있다(`src/models.ts:1528-1540`). 이 값은 무료 사용을 입증하지 않는다. 또한 `costIsEstimated`는 어떤 제공자에서는 토큰 자체 추정을, 다른 제공자에서는 기록된 토큰의 비용 추정을 나타내므로 하나의 신뢰도 의미로 뭉뚱그리면 안 된다.

로컬 기록을 읽는다는 사실만으로 '이 PC에서 생성한 사용량'이 증명되지는 않는다. 복사된 세션, 원격 에이전트 기록의 로컬 미러, 계정 단위 CSV에는 다른 기기의 활동이 포함될 수 있다. 수집 위치와 사용이 발생한 위치는 별도 속성이다.

`src/token-estimate.ts:1`은 문자 수를 4로 나누어 올림하는 추정식을 제공한다. 컨텍스트 예산에는 시스템 기본 10,400, 도구당 400, skill frontmatter당 80 등의 추정 상수도 있다(`src/context-budget.ts:8`). 이 값은 제공자 usage 기록의 실측 토큰과 같은 정확도로 취급하면 안 된다.

활동 분류는 모델이 작업 의도를 이해하는 방식이 아니라 도구 패턴과 정규식이다. `src/classifier.ts:9-13`의 feature/debug/refactor/research 등 키워드는 영어 중심이다. 한글만 있는 대화는 같은 의미의 영어 프롬프트와 다른 분류로 갈 수 있다. 편집 도구가 있으면 coding이 되더라도 feature/debugging으로의 세분화는 키워드에 영향을 받는다. 이는 코드에서 도출한 한계이며 실제 사용자 세션으로 정확도를 측정하지 않았다.

## Windows 상주 표시와 AICap의 차이

CodeBurn의 Windows companion은 Tauri의 트레이 아이콘을 사용한다. 짧은 비용 문자열을 작은 비트맵으로 그려 **별도 숫자 아이콘**으로 표시한다(`windows/src-tauri/src/lib.rs:604-621`). 이는 AICap의 Explorer 작업표시줄 창에 위젯을 `SetParent`로 붙이는 방식과 다르다.

Capacity Dock은 투명·장식 없음·always-on-top·skip_taskbar 속성의 독립 창이다(`windows/src-tauri/src/dock.rs:1387-1399`). 따라서 작업표시줄 내부 삽입과 동일한 기능으로 취급해서는 안 된다. Explorer 창 구조 의존이 줄어드는 설계로 해석할 수 있지만 실제 안정성 우위를 측정한 것은 아니다.

자동 시작은 HKCU Run 등록이며 상태 조회는 등록값 존재에 해당한다. StartupApproved나 실제 로그인 후 실행 성공까지 입증하지 않는다. 초기 표시용 저장 상태, DPI/theme 대응, 모니터 work area 및 전원 상태별 갱신 코드도 있다. 코드상 기본 갱신은 팝오버 열림 30초, AC idle 120초, 배터리 150초, 절전 300초다. 문서의 열림 60초 설명과 차이가 있어 코드 기준으로 기록했다.

## 현재 PC 비율과 기기 합계

`sharing/host.ts:177-205`는 현재 기기와 페어링한 원격 기기에 같은 기간 쿼리를 보낸다. 응답 가능한 기기의 수치를 합산하며 실패한 기기는 별도 오류로 남긴다.

**이 합계는 제공자 계정 전체 사용량이 아니다.** 꺼져 있거나 연결되지 않은 기기는 빠지고, 같은 기록이 여러 기기에 있으면 중복될 수 있다. 기기 fingerprint 중복 제거와 호출/세션 중복 제거는 다르다. 해당 합산 경로에는 기기간 이벤트 중복 제거가 없으며 세션 합계를 고유 세션 수로 표시하지 못한다는 주석도 있다(`sharing/host.ts:99-102`).

TokenTrailer에서 이 방식을 참고한다면 비율의 이름은 '집계된 기기 중 이 PC 비중'에 해당한다. '계정 전체에서 내가 사용한 비율'을 만들려면 계정·기간·단위가 일치하는 전체 분모와 중복·누락 처리 계약이 추가로 필요하다.

## 네트워크와 변경 가능성이 있는 기능

기본 로컬 분석, 기기 공유, 조직 sync, 계정 quota, 자동 개입을 구분해야 한다. 공식 사이트의 로컬 중심 설명을 모든 옵션의 무전송·무변경 보장으로 확대하지 않는다.

| 경로 | 확인한 동작과 한계 |
|---|---|
| 로컬 웹 | `127.0.0.1` listen, Host/Origin 검사. 웹 제공 자체와 외부 공유는 별도 |
| 기기 공유 | HTTPS, bearer token, 인증서 fingerprint pinning. 프로젝트·세션 상세 등을 제거하지만 일부 집계명 유지 |
| 공유 sanitizer | 특정 필드를 제거하고 나머지를 복사하는 방식. 모든 미래 식별정보가 자동 차단되는 allowlist는 아님 |
| 조직 OTLP sync | 공급자·모델·토큰·비용·프로젝트 basename·도구·기기 식별자 및 선택적 작업/PR 정보. 동의 fingerprint와 송신 ledger 존재 |
| sync 기기 ID | hostname:username의 SHA256 앞 16자리. 안내문의 random identifier와 구현이 다름 |
| Codex quota | OAuth 갱신 후 회전된 토큰을 auth.json에 저장할 수 있음. 단순 읽기 명령으로 취급하면 안 됨 |
| Cursor sync | 계정 CSV 다운로드 경로 존재. 현재 PC 기록과 계정 데이터의 범위 구분 필요 |
| act / guard | 설정 적용·undo, Claude hook 설치·제거 및 예산 차단. 관찰 기능과 별도 |
| MCP | 집계가 모델/클라이언트로 전달될 수 있음. 프로젝트명 기본 가명화 및 실제명 포함 옵션 |

이 조사에서는 위 동작을 실행하지 않았다. 코드 경로의 존재를 확인한 것이며 실제 서버·OS 보호·개인정보 전송 결과를 검증한 것은 아니다.

## TokenTrailer에 참고할 방향

다음은 요구사항 변경이 아닌 검토 후보다.

- 첫 화면은 '언제 많이 썼는지 → 어떤 프로젝트/세션인지 → 어떤 작업/도구인지' 순서로 좁혀 간다.
- 토큰을 기본 분석축으로 삼고 비용·요금제 한도는 별도 지표로 표시한다.
- 실측/추정, 마지막 갱신, 누락된 기기, 데이터 출처를 수치와 함께 표시한다.
- 작업 분류 결과를 정답처럼 고정하지 않는다. 한국어·도구 차이와 사용자가 정정할 방법을 요구사항에서 검토한다.
- 기기 비율은 분모·기간·계정·중복 제거가 확보된 범위까지만 표시한다.
- Windows 트레이/떠 있는 위젯/작업표시줄 삽입 중 무엇을 지원할지 구분하고 각각의 복구 시나리오를 정한다.
- 단순 모니터링에 계정 파일 수정, 자동 모델 요청, hook 설치를 암묵적으로 포함하지 않는다.

## 검증 범위

배포 무결성, 파일·소스맵 식별, 공개 tag 대조, REA 정적 파싱, 주요 기능의 코드 흐름을 확인했다. 실제 개인 로그 수집, 전체 테스트 스위트, 인증·quota·동기화·hook·백업·업데이트, Windows 상주 앱의 실행 및 재부팅 검증은 하지 않았다.

REA 그래프는 두 번 모두 partial이다. 미해결 관계나 검색 부재를 기능 부재의 증거로 사용하지 않았다. 별도 데스크톱/트레이의 결과는 공개 tag 소스 기준이며 배포 실행 파일의 역컴파일 결과가 아니다.

분석 중 설치·실행·설정 변경·커밋·푸시는 수행하지 않았다. 기존 AICap 보고서와 프로젝트 목표는 유지했다.
